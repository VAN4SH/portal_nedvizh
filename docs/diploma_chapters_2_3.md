# Глава 2. Проектирование веб-приложения для поиска и размещения объявлений о недвижимости

## 2.1 Описание разрабатываемого веб-приложения

Разрабатываемое веб-приложение «Недвижимость Pro» представляет собой информационную систему для публикации, поиска и просмотра объявлений о продаже и аренде объектов недвижимости. Основная идея проекта заключается в создании удобного веб-портала, который объединяет возможности открытого каталога недвижимости и личного кабинета пользователя. Система позволяет посетителям просматривать список объектов, фильтровать объявления по ключевым параметрам, изучать подробную карточку объекта, а зарегистрированным пользователям — добавлять собственные объявления, редактировать сведения о них и управлять личными данными.

Назначение приложения состоит в автоматизации типовых операций, возникающих при работе с объявлениями о недвижимости. В традиционном варианте такие операции выполняются вручную: пользователь ищет подходящие предложения на разных площадках, продавец или агент отдельно готовит описание объекта, загружает фотографии и передает контактные данные потенциальным покупателям. В разрабатываемой системе эти действия объединяются в едином интерфейсе. Посетитель сайта получает быстрый доступ к каталогу, а владелец объявления может самостоятельно разместить объект и поддерживать сведения в актуальном состоянии.

С точки зрения пользователя приложение должно быть простым и понятным. Главная страница знакомит посетителя с сервисом, показывает избранные и последние объявления, а также предоставляет быстрый переход к каталогу. Раздел объявлений содержит список объектов недвижимости и фильтры, позволяющие ограничить выдачу по типу недвижимости, городу и диапазону цены. Страница отдельного объявления отображает основную информацию об объекте: название, описание, стоимость, адрес, город, площадь, количество комнат, сведения об авторе и контактные данные.

Функциональность веб-приложения можно разделить на несколько основных блоков:

1. **Публичный каталог недвижимости.** Доступен всем посетителям сайта без авторизации. Включает просмотр главной страницы, переход к списку объявлений, фильтрацию объектов и просмотр подробной карточки.
2. **Регистрация и авторизация пользователей.** Позволяет создать учетную запись, выполнить вход в систему и получить доступ к защищенным функциям.
3. **Личный кабинет.** Предоставляет зарегистрированному пользователю сведения о профиле, статусе пользователя, контактных данных и статистике по размещенным объявлениям.
4. **Управление объявлениями.** Авторизованный пользователь может добавлять новые объявления, просматривать список собственных объектов, редактировать их параметры и удалять устаревшие записи.
5. **Загрузка изображений.** При создании объявления пользователь может добавить основное изображение и дополнительные фотографии объекта. Изображения сохраняются в файловой структуре приложения, а сведения о них связываются с записью в базе данных.
6. **Информационные страницы.** Сайт содержит страницы «О нас» и «Контакты», необходимые для представления сервиса и обратной связи.
7. **API для вспомогательных данных.** В приложении предусмотрены маршруты, возвращающие список городов и типов недвижимости в формате JSON. Эти данные могут использоваться для динамических элементов интерфейса.

Архитектурно приложение реализовано как серверное веб-приложение на языке Python с использованием фреймворка Flask. Flask отвечает за маршрутизацию HTTP-запросов, обработку форм, рендеринг HTML-шаблонов и передачу данных между пользовательским интерфейсом и базой данных. Для работы с базой данных применяется Flask-SQLAlchemy, предоставляющий объектно-реляционное отображение: таблицы базы данных описываются в виде Python-классов, а операции с записями выполняются через объектную модель. Для управления пользовательскими сессиями используется Flask-Login.

В качестве хранилища данных используется SQLite. Такой выбор оправдан для учебного проекта и прототипа, поскольку SQLite не требует отдельного сервера базы данных, хранит данные в одном файле и легко интегрируется с Flask-приложением. При необходимости дальнейшего развития системы архитектура с SQLAlchemy позволяет перенести приложение на другую реляционную СУБД, например PostgreSQL, без полной переработки бизнес-логики.

Интерфейсная часть реализована с применением HTML-шаблонов Jinja2, CSS, JavaScript и компонентов Bootstrap. Базовый шаблон содержит навигационную панель, область вывода системных сообщений, основной блок страницы и подвал сайта. Остальные страницы наследуют общую структуру и переопределяют только содержательную часть. Такой подход снижает дублирование кода и обеспечивает единый внешний вид приложения.

Основными сущностями предметной области являются пользователь и объявление. Пользователь хранит учетные и контактные данные, а также признак агента по недвижимости. Объявление описывает конкретный объект недвижимости и содержит название, описание, цену, тип объекта, город, адрес, площадь, количество комнат, сведения об изображениях и ссылку на автора объявления. Между пользователем и объявлениями установлена связь «один ко многим»: один пользователь может создать несколько объявлений, но каждое объявление принадлежит только одному пользователю.

Сценарий использования приложения для посетителя сайта начинается с открытия главной страницы. Далее пользователь может перейти в каталог объявлений, применить фильтры и открыть карточку интересующего объекта. Если посетитель хочет разместить собственное объявление, он должен зарегистрироваться или авторизоваться. После входа в систему ему становятся доступны личный кабинет, страница добавления объявления и раздел «Мои объявления». При создании объявления система проверяет обязательные поля, сохраняет данные в базе и при успешном завершении перенаправляет пользователя на страницу созданного объекта.

Для владельца объявления важным сценарием является поддержание информации в актуальном состоянии. Он может открыть список своих объявлений, выбрать конкретный объект, изменить цену, описание, адрес, характеристики или главное изображение. При удалении объявления система удаляет запись из базы данных и связанные изображения из файлового хранилища, если они были загружены пользователем.

Таким образом, проектируемая система решает задачу создания небольшого, но целостного веб-портала недвижимости. В приложении присутствуют основные элементы современных веб-сервисов: авторизация, личный кабинет, работа с базой данных, загрузка файлов, фильтрация данных, шаблонизация страниц и обработка ошибок.

## 2.2 Объектно-ориентированное моделирование функционирования веб-приложения

Для проектирования приложения использованы UML-диаграммы, позволяющие представить систему с разных точек зрения. Диаграмма вариантов использования описывает функциональные возможности с позиции пользователя. Диаграммы состояний отражают поведение системы при выполнении отдельных сценариев. Диаграмма классов демонстрирует структуру основных сущностей и служебных компонентов. Диаграмма пакетов показывает организацию приложения по модулям и зависимостям.

На рисунке 2.1 представлена диаграмма вариантов использования веб-приложения. В системе выделены три основных актора: гость, зарегистрированный пользователь и агент или продавец недвижимости. Гость представляет посетителя сайта, который не прошел авторизацию. Ему доступны публичные функции: просмотр главной страницы, поиск и фильтрация объявлений, просмотр карточки объекта, отправка сообщения через форму контактов, регистрация и авторизация.

Зарегистрированный пользователь является расширением гостя. После входа в систему он получает доступ к личному кабинету, может редактировать профиль и просматривать собственные объявления. Агент или продавец является частным случаем зарегистрированного пользователя и дополнительно выполняет действия по управлению объявлениями: добавляет новые объекты, редактирует существующие и удаляет устаревшие записи.

На диаграмме также выделено хранилище данных, включающее SQLite-базу и каталог изображений. С ним взаимодействуют варианты использования, связанные с поиском, добавлением, редактированием и удалением объявлений. Такое отображение показывает, что наиболее важная часть бизнес-логики приложения связана с корректной записью и чтением данных о недвижимости.

Диаграмма вариантов использования позволяет уточнить границы системы. Например, звонок по номеру телефона или реальное заключение сделки не входят в область ответственности приложения. Система только предоставляет информацию об объекте и контактах автора объявления. Это важно для корректного определения функциональных требований.

### Диаграмма состояний процесса авторизации

[Вставить рисунок 2.2: файл `docs/diagrams/state_authorization.drawio`, экспортировать из Draw.io в PNG. Подпись: «Рисунок 2.2 – Диаграмма состояний процесса регистрации и авторизации пользователя».]

На рисунке 2.2 показана диаграмма состояний, описывающая процесс регистрации и авторизации пользователя. Начальным состоянием является неавторизованный посетитель. Далее пользователь выбирает одно из двух действий: вход в существующую учетную запись или создание новой учетной записи.

При регистрации система отображает форму, в которой пользователь указывает имя, адрес электронной почты, пароль и подтверждение пароля. После отправки формы выполняется проверка данных. Система контролирует минимальную длину имени пользователя и пароля, проверяет корректность адреса электронной почты, совпадение пароля и подтверждения, а также уникальность имени пользователя и электронной почты. Если проверка не пройдена, пользователь возвращается к форме регистрации и получает сообщение об ошибке. Если данные корректны, система создает запись пользователя в базе данных, сохраняет хэш пароля и выполняет вход.

При авторизации пользователь вводит email и пароль. Система ищет пользователя в базе данных и сравнивает введенный пароль с сохраненным хэшем. При неуспешной проверке пользователь остается на странице входа и получает сообщение о неверных данных. При успешной проверке создается пользовательская сессия, после чего пользователь переходит на главную страницу или на страницу, которую пытался открыть до авторизации.

Данная диаграмма отражает важное свойство приложения: защищенные страницы доступны только после успешного входа. Это относится к личному кабинету, странице добавления объявления, списку собственных объявлений и операциям редактирования или удаления.

### Диаграмма состояний жизненного цикла объявления

[Вставить рисунок 2.3: файл `docs/diagrams/state_listing_lifecycle.drawio`, экспортировать из Draw.io в PNG. Подпись: «Рисунок 2.3 – Диаграмма состояний жизненного цикла объявления».]

На рисунке 2.3 представлена диаграмма состояний объявления о недвижимости. Жизненный цикл начинается с перехода авторизованного пользователя на страницу добавления объявления. На этом этапе объект еще не существует в базе данных, а пользователь заполняет форму с основными характеристиками недвижимости.

После отправки формы система выполняет валидацию. Проверяются обязательные поля: название, описание, адрес и город. Отдельно проверяется цена: она должна быть числом и иметь положительное значение. Если данные некорректны, объявление остается в состоянии черновика формы, а пользователь получает сообщение об ошибке. Если проверка успешна, создается объект модели Listing, обрабатываются загруженные изображения, после чего запись сохраняется в базе данных.

После публикации объявление становится доступным в каталоге и может быть найдено другими пользователями через фильтры. Автор объявления может открыть страницу редактирования. При изменении данных система обновляет запись и дату последнего изменения. Если пользователь загружает новое главное изображение, старый файл может быть удален из каталога изображений, чтобы не оставлять неиспользуемые файлы.

Конечным состоянием жизненного цикла является удаление объявления. При удалении проверяется, что текущий пользователь является владельцем записи. Затем система удаляет основные и дополнительные изображения, если они были загружены, удаляет запись из базы данных и возвращает пользователя к списку его объявлений. Проверка владельца является важным элементом безопасности: пользователь не должен иметь возможность редактировать или удалять чужие объявления.

### Диаграмма классов

[Вставить рисунок 2.4: файл `docs/diagrams/class_diagram.drawio`, экспортировать из Draw.io в PNG. Подпись: «Рисунок 2.4 – Диаграмма классов веб-приложения».]

На рисунке 2.4 показана диаграмма классов приложения. Центральными классами являются `User` и `Listing`. Они одновременно выступают моделями предметной области и моделями базы данных, поскольку наследуются от `db.Model`.

Класс `User` описывает учетную запись пользователя. Он содержит идентификатор, имя пользователя, email, хэш пароля, номер телефона, признак агента и дату создания учетной записи. Методы `set_password` и `check_password` инкапсулируют работу с паролем. Пароль не хранится в открытом виде: при сохранении используется хэширование, а при входе выполняется проверка соответствия введенного пароля сохраненному хэшу. Также класс наследует функциональность `UserMixin`, которая требуется Flask-Login для определения состояния пользователя в сессии.

Класс `Listing` описывает объявление о недвижимости. В нем хранятся название объекта, описание, цена, тип недвижимости, количество комнат и санузлов, площадь, адрес, город, признак избранного или премиального объявления, имя главного изображения, список дополнительных изображений, идентификатор автора, дата создания и дата обновления. Связь между `User` и `Listing` реализована через внешний ключ `user_id` и отношение `listings`. Это позволяет получить все объявления пользователя и, наоборот, автора конкретного объявления.

Кроме моделей на диаграмме показаны служебные компоненты. `Config` хранит настройки приложения: секретный ключ, строку подключения к базе данных, каталог загрузки изображений, максимальный размер файла и допустимые расширения. `LoginManager` отвечает за работу пользовательских сессий и загрузку пользователя по идентификатору. `SQLAlchemy` является слоем доступа к базе данных. Компонент Flask routes объединяет обработчики HTTP-запросов: главную страницу, каталог, карточку объявления, регистрацию, вход, профиль и CRUD-операции с объявлениями.

Такая структура классов соответствует архитектуре небольшого Flask-приложения: модели данных находятся рядом с маршрутами, а взаимодействие с базой выполняется через ORM. Для дальнейшего развития проекта классы и маршруты можно вынести в отдельные модули и разделить приложение на blueprints, однако для учебного проекта текущая структура остается понятной и достаточной.

### Диаграмма пакетов

[Вставить рисунок 2.5: файл `docs/diagrams/package_diagram.drawio`, экспортировать из Draw.io в PNG. Подпись: «Рисунок 2.5 – Диаграмма пакетов веб-приложения».]

На рисунке 2.5 представлена диаграмма пакетов, отражающая логическую организацию проекта. На клиентском уровне расположен браузер пользователя, который отображает HTML-страницы, выполняет JavaScript-код и загружает CSS-стили, изображения и шрифты. Пользователь взаимодействует с формами, кнопками, фильтрами и навигацией, после чего браузер отправляет HTTP-запросы на сервер.

Серверный уровень представлен Flask-приложением. Внутри него можно выделить несколько логических пакетов: маршруты, аутентификация, модели, работа с изображениями, шаблоны и статические файлы. Пакет маршрутов принимает запросы, вызывает бизнес-логику и выбирает шаблон для ответа. Пакет аутентификации отвечает за регистрацию, вход, выход и проверку доступа к защищенным страницам. Пакет моделей описывает структуру данных и связи между сущностями. Пакет обработки изображений проверяет расширения файлов, формирует безопасные имена и сохраняет изображения в каталог проекта.

Уровень хранения данных включает SQLite-базу и файловое хранилище изображений. В базе сохраняются пользователи и объявления, а изображения хранятся в каталоге `static/images/properties`. Такое разделение оправдано, поскольку хранение файлов непосредственно в базе данных усложнило бы работу приложения и увеличило размер базы. В базе достаточно хранить имя файла, связанное с объявлением.

Диаграмма пакетов показывает, что приложение построено по классической схеме web-приложения: клиент отправляет запросы, сервер обрабатывает их, обращается к базе данных и возвращает HTML-страницу. Такая архитектура хорошо подходит для учебного проекта, легко запускается локально и может быть расширена при необходимости.

Разработанное приложение демонстрирует полный цикл работы веб-сервиса: пользователь регистрируется, входит в систему, создает объявление, просматривает его в каталоге, редактирует данные и при необходимости удаляет запись. Реализованы базовые механизмы безопасности: хэширование паролей, защита маршрутов авторизацией и проверка владельца объявления перед изменением данных. Использование Flask, SQLAlchemy и Bootstrap позволило создать функциональное приложение с понятной архитектурой и адаптивным интерфейсом.

В дальнейшем проект может быть расширен. Однако уже текущая версия приложения решает основную задачу дипломного проекта — создание веб-приложения для публикации и поиска объявлений о недвижимости.
